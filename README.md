# SQL Server Query Tuning - Case Study

Six real-world SQL Server performance problems, reproduced on a 2-million-row database, fixed, and **measured**. Every number below comes from an actual benchmark run (`bench/TuningBench`) - nothing is estimated - and every before/after has its actual execution plan saved in [`plans/`](plans) so you can open it in SSMS and check for yourself.

The schema and data are 100% invented (a fictional contractor staffing agency: clients, contractors, placements, weekly timesheets, invoices, payments) and generated by a deterministic set-based script, so anyone can rebuild the exact same database and reproduce the results.

## Results

Median of 7 measured runs per phase, warm cache, after one discarded warm-up run.
SQL Server 2025 Express LocalDB on a 4-core desktop (details [below](#test-environment)).

|---|---|---|---|---|---|---|---|

> Reading the numbers: **logical reads** (8 KB pages touched in memory) are the most reliable measure - they are exact and do not depend on the hardware or on what else the machine is doing. Elapsed and CPU times are real but come from a dev desktop; on a busy production server with a cold cache the "before" queries would also pay for physical I/O and suffer more. Sub-millisecond "after" timings are at the noise floor of the measurement, and CPU time is reported by Windows in ~15.6 ms ticks, which is why fast queries show 0.

## The scenarios in one paragraph each

**01 - Non-SARGable predicate.** `WHERE YEAR(SubmittedAt) = 2025 AND MONTH(SubmittedAt) = 6` hides the column inside functions, so the index on `SubmittedAt` can only be scanned end-to-end (2M rows). Rewriting it as `SubmittedAt >= '20250601' AND SubmittedAt < '20250701'` returns the same rows with a range seek over ~76k rows. No new index needed. → [details](scenarios/01-non-sargable-date-filter/README.md)

**02 - Implicit conversion.** `AddWithValue()` / untyped ORM strings arrive as `NVARCHAR(4000)`; the column is `VARCHAR(20)`. SQL Server converts the *column* for every row (`CONVERT_IMPLICIT`, plan warning "may affect SeekPlan") and scans the whole index for a single-row lookup. Typing the parameter as `VARCHAR(20)` gives a 6-read seek. → [details](scenarios/02-implicit-conversion/README.md)

**03 - Missing covering index.** A client/quarter report could only use a single-column `ClientId` index; fetching the other columns would mean 60,000 key lookups, so the optimizer scanned the whole 2M-row table instead. A composite index keyed `(ClientId, WeekEnding)` with the read columns `INCLUDE`d turns it into one 30-page seek. → [details](scenarios/03-covering-index/README.md)

**04 - Cursor → set-based.** A balance-refresh job processed invoices one at a time: ~74,000 statements and - measured with `sys.dm_exec_session_wait_stats` - 18,459 `WRITELOG` waits, one log flush per auto-committed row. A single `UPDATE ... FROM` with an aggregated join does the same work in one statement and one transaction. → [details](scenarios/04-cursor-to-set-based/README.md)

**05 - Parameter sniffing.** A procedure's plan was compiled for a 3-day window (seek + key lookups) and reused for a 21-month re-sync - 1.27 million key lookups and 4 million reads. `OPTION (RECOMPILE)` lets it pick a single scan for big windows. The write-up compares `OPTIMIZE FOR`, `OPTIMIZE FOR UNKNOWN`, index changes, plan guides / Query Store hints, and shows (measured) that SQL Server 2022+ Parameter Sensitive Plan optimization fixes the equality-predicate version of this problem but not the range-predicate one. → [details](scenarios/05-parameter-sniffing/README.md)

**06 - Deep pagination.** `OFFSET 1,499,950 ROWS FETCH NEXT 50` sorts 2M rows (spilling to tempdb) to return 50. Keyset pagination - "the 50 rows after `(SubmittedAt, TimesheetId)` of the last row shown" - seeks straight there; page 30,000 now costs the same as page 1. → [details](scenarios/06-keyset-pagination/README.md)

## How to reproduce

Requirements: Windows with SQL Server LocalDB (installed with Visual Studio or the SQL Server Express installer) or any SQL Server 2019+ instance, `sqlcmd`, and the .NET 11 SDK.

```powershell
# 1. Build the database (about 75 seconds on the test machine)
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -b -i sql\00_create_database.sql
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -b -i sql\01_schema.sql
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -b -i sql\02_seed.sql

# 2. Run the benchmark (about 2 minutes); rewrites results/ and plans/
dotnet run -c Release --project bench\TuningBench -- --runs 7

# Options: --server <name>  --database <name>  --runs <n>  --scenario 03  --no-plans
```

`-C` trusts the server certificate (needed by the newer ODBC-based `sqlcmd`). To use another instance pass `--server`; the scripts only need a database called `TuningDemo` (or pass `--database`).

To look at a scenario by hand in SSMS: run its `before_setup.sql` (if any), then `before.sql` with *Include Actual Execution Plan* (Ctrl+M) and `SET STATISTICS IO, TIME ON`, then the same for `after_setup.sql` / `after.sql`. For scenario 05, run the setup and the query **in the same session** - SSMS's `ARITHABORT ON` gives it a separate plan-cache entry from the one the benchmark primed.

### How the benchmark measures

- One dedicated connection (no pooling) per phase. The optional setup script runs first, unmeasured, then one warm-up execution is discarded, then *N* measured executions.
- **Logical reads and CPU** are the delta of `sys.dm_exec_sessions` (`logical_reads`, `cpu_time`) for the benchmark's own session around each execution. Unlike `SET STATISTICS IO/TIME` output, this works for multi-statement batches and cursors that run tens of thousands of statements.
- **Elapsed** is a client-side `Stopwatch` around execution plus reading every returned row - what the application experiences.
- **Plans**: one extra execution per phase with `SET STATISTICS XML ON`; each actual plan is written to `plans/<scenario>__<phase>.sqlplan`. For the cursor, the first plan of each distinct statement is kept.

## Test environment

| | |
|---|---|
| SQL Server | Microsoft SQL Server 2025 (RTM-CU3) (KB5077896) - 17.0.4025.3 (X64), **Express Edition (64-bit)** running as **LocalDB** |
| Database | compatibility level 170, recovery SIMPLE, collation `SQL_Latin1_General_CP1_CI_AS` |
| Server settings | defaults: MAXDOP 0, cost threshold for parallelism 5 |
| Hardware | Intel Core i3-9100 @ 3.60 GHz (4 cores / 4 threads), 16 GB RAM, developer desktop |
| OS | Windows 11 Pro (build 26300) |

LocalDB is Express Edition: it is limited to the lesser of 1 socket / 4 cores and ~1.4 GB of buffer pool and has no batch mode on rowstore, so absolute times are those of a modest machine. The *relative* improvements - and the logical reads, which are exact - are what carry over to production servers.
